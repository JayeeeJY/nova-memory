# Nova Memory 版本与迭代管理

从第一阶段公开源码基线开始，产品使用统一版本号。当前基线为 **v0.1.0 · 本地源码预览版**，日期为 2026-11-22。第一阶段“形成完整本地产品基础并公开 GitHub 源码”的目标由作者确认完成；具体能力范围、已知限制与后续签名发行工作分别保留。

## 版本怎样递增

| 类型 | 示例 | 用途 |
| --- | --- | --- |
| 修复版 | v0.1.1、v0.1.2 | 缺陷、体验修正、说明与适配维护，不改变既有数据含义 |
| 功能迭代 | v0.2.0、v0.3.0 | 一组完整、可验收的新能力；0.x 阶段的不兼容变化也在这里明确说明 |
| 验收候选 | v0.2.0-rc.1 | 功能已冻结，供集中验收；之后的修正继续编号 |
| 稳定基线 | v1.0.0 | 达到届时明确的稳定交付标准后再定义，不因阶段一完成自动宣称达到 |

不是每次提交都发一个版本。日常改动在主分支和 Unreleased 中累积；有明确交付范围、通过对应检查后形成版本。公开标签和已发布版本的含义保持不变，修正通过新版本交付。

## 统一来源与独立编号

- `VERSION`：产品版本的唯一来源。
- `Cargo.toml` 与 `Cargo.lock`：由版本命令同步的构建元数据；CLI 版本随 Cargo 构建取得。
- 打包脚本：运行包读取 `VERSION`；macOS 展示其数字部分，预发布完整版本以发布记录和运行包元数据为准。现有构建号 `1` 是包内构建字段，不是另一个产品版本。
- `CHANGELOG.md`：每版的用户可见改动、兼容性、验证与已知限制。
- GitHub tag：`v` 加产品版本，固定到确切代码提交；源码预览使用预发布标记。GitHub Release 不是“已提供正式安装包”的证明，附件与签名状态单独说明。
- 旧方案 v3.17、N2a、M1 等是规划编号；`nova.query.v0.1`、包格式和数据库版本是协议/存储合同。它们不随产品版本机械递增。

## 每轮开发怎么推进

1. 定义本轮版本目标、包含事项、暂不包含事项和验收方式。
2. 完成代码与文档，变更累计进 Unreleased，必要时建立 Issue/PR。
3. 功能、文档和对应检查收口；模型、真实客户端、设备等只记录实际完成的验证，不用重复模型演练拖延无关功能。
4. 需要集中验收时使用 rc 候选，修复后继续候选编号。
5. 发布前核对版本号、兼容性与迁移/备份说明，创建固定 tag 与 Release。
6. 验收结论和遗留事项跟着该版本保留，下一轮另起版本。

首次 v0.1.0 用现有源码和作者确认建立基线，不重跑无关模型或云环境验收。下个功能迭代目标为 v0.2.0；范围在下一轮开始前按本地体验优先确定。

## 操作命令

```sh
python3 scripts/version.py show
python3 scripts/version.py check
python3 scripts/version.py set 0.1.1 --dry-run
python3 scripts/version.py set 0.1.1
```

`set` 只修改版本元数据，不打包、不迁移数据、不创建标签、不公开发布。修改后为新版本添加带日期的更新日志，再执行检查和该改动所需的测试。包格式或旧备份支持不得仅因为产品号变化而收窄；相关改动必须另有兼容性验证。

发布时先运行 `python3 scripts/version.py check --tag v0.1.0`（替换为实际目标号），确认 tag 指向经过检查的提交。签名安装包、真实客户端和实际设备验证分别记录，不以一个“发布成功”统称。
